# Code Intelligence Workflow（LSP + AST）

## 目标

让代码修改建立在可验证的代码关系上，而不是只依赖文本搜索和猜测。工具可用时优先使用 DSH 提供的：

- LSP：符号定义、引用、实现、类型和文档。
- ast_grep：按 AST 结构查找同类代码；只读，不执行 rewrite。

不要为了“看起来用了工具”而对简单任务增加无意义查询。

## 工具选择

| 场景 | 首选 | 原因 |
|---|---|---|
| 不知道函数、类型或类在哪里定义 | LSP goToDefinition | 按语义跳转，避免同名文本误判 |
| 修改公共函数、接口、类型或 API | LSP findReferences | 盘点真实调用方 |
| 查某接口或抽象类的实现 | LSP goToImplementation | 找实现关系而不是字符串相似处 |
| 需要知道表达式、参数或返回值类型 | LSP hover | 获取语言服务的类型信息 |
| 查所有同类调用、声明或旧写法 | ast_grep | 按语法结构匹配，减少注释和字符串误报 |
| 单点且文件、符号、行号都已知的小改动 | read 加定向编辑 | 不需要强行启动分析工具 |
| 文档、配置或非代码任务 | 普通文件工具 | AST/LSP 没有额外收益 |

## 修改前流程

### 普通功能或 bug 修复

1. 读取相关文件和项目规则。
2. 如果符号位置或类型不确定，先用 LSP goToDefinition 或 hover。
3. 如果会影响公共 API，先用 LSP findReferences。
4. 如果改动模式会出现多处，使用 ast_grep 盘点结构化匹配。
5. 根据实际结果确定修改范围，再编辑文件。

### 批量重构或迁移

1. 先用 ast_grep 做只读盘点，不要直接改写。
2. 必要时用 LSP 确认关键符号的定义和引用关系。
3. 记录匹配数量、文件范围和明显例外。
4. 分批修改，避免一次性改动无法审查。
5. 修改后重新运行同一个 AST 查询，确认旧结构是否还存在。
6. 对公共符号再运行 LSP 引用检查或项目测试。

### 高风险改动

以下情况默认要求先做 LSP 或 AST 分析：

- 修改导出函数、公共类型、接口、路由、序列化格式或数据库访问。
- 删除或重命名符号。
- 将一个 API 或库调用迁移到另一个 API 或库。
- 需要跨多个目录修改。
- 用户明确要求先分析影响范围或不要漏改。

## 工具调用规则

### LSP

调用形状：

    lsp({ operation, file_path, line, character })

支持的 operation：

- goToDefinition
- findReferences
- goToImplementation
- hover

line 和 character 从 1 开始；character 按 UTF-16 列计算。结果为空时不要把“没有结果”解释成“没有引用”，要考虑文件是否已打开、项目配置是否完整、语言服务是否支持该关系。Python 使用 Pyright，Kotlin 使用 standalone language server；二者都要求文件扩展名、工作区根目录和项目配置正确。

### ast_grep

调用形状：

    ast_grep({ pattern, path?, lang? })

规则：

- path 必须是当前工作区内的相对路径。
- 单文件可省略 lang，按扩展名推断。
- 目录搜索不指定 lang 时默认按 JavaScript 查询；TypeScript、Python、Kotlin 等目录请显式传语言。扩展名推断包含 .py/.pyi -> python 和 .kt/.kts -> kotlin。
- 使用结构化 pattern，例如 fetch($$$) 或 function $NAME($$$) { $$$ }。Python 函数可用 def $F($$$): $$$；带返回注解时用 def $F($$$) -> $T: $$$。Kotlin typed function 可用 fun $F($$$): $T { $$$ }。
- 只读；不要假设它会修改文件。
- 输出超限时缩小 path 或 pattern，不要依据残缺输出继续改代码。
- 不要把 AST 查询结果当作完整语义关系；跨文件定义和引用使用 LSP。Kotlin LSP 是 Alpha，项目导入和 Gradle/Maven 配置可能影响结果；先确认实际返回，再报告能力。

## 修改后复查

至少选择一种与修改风险匹配的复查：

- 单点逻辑修改：运行相关测试或局部检查。
- 批量结构修改：重新执行 AST 查询，确认旧结构已清零或剩余项已解释。
- 公共符号修改：LSP 查引用，并运行类型检查或测试。
- 重命名或删除：确认旧名称没有意外残留，并检查新名称的定义和引用。

报告时区分：

- 工具实际返回的事实；
- 测试实际覆盖的范围；
- 尚未验证的语言、平台、路径或运行时场景。

## 工具不可用时

如果当前宿主尚未加载工具、语言服务器没有配置、或查询失败：

1. 不要假装已经完成 AST/LSP 分析。
2. 可以使用 read、grep 等普通工具做有限调查。
3. 明确说明这是文本级或降级检查，并指出需要何时重新验证。
4. 对高风险改动，不要把降级检查包装成完整影响范围分析。

## 典型提示词

用户没有指定流程时，按上面的风险判断自行选择。以下任务可以直接触发本 Skill 的完整流程：

- 先查这个函数的定义和所有引用，再改。
- 先用 AST 找出所有旧 API 调用，再迁移。
- 修改后用 AST 检查旧写法是否还有残留。
- 这个重构不要漏掉跨文件调用。

Skill 的职责是指导工具选择和验证顺序；它不替代项目规则，不授权重启宿主，不允许修改用户未授权的文件或数据。
